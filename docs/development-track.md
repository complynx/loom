## Порядок и правила завершения

1. Этап A — целевые контракты и воспроизводимая поставка.
2. Этап B — первый реальный сервис и клиентский сценарий.
3. Этап C — эксплуатация, restore и ограниченный pilot.
4. Этап D — долгие сессии и устранение функциональных пробелов.
5. Этап E — нагрузка и масштабирование.
6. Этап F — дополнительные способы подключения и сценарии.

Этапы A, B и C образуют release gate для обычного запуска. Метрики уже реализованы; их серверную приёмку и подготовку backup можно выполнять параллельно после подготовки deployment. Каждый этап проходит focused behavioral tests, свежий независимый review loop при изменении кода и интеграционный gate для затронутых границ. Повторять весь набор следует при изменении общей границы или перед релизом, а не после каждой правки документации. Push в main запускает уже согласованные автоматические публикацию и deploy trigger. Применение серверного profile и изменения соседних сервисов остаются отдельной областью работы; эта актуализация документов ничего не публикует.

Для каждой выполненной задачи сохранять commit/PR, сценарий проверки и ссылку на evidence. Локальный PASS, установленная интеграция и production acceptance — отдельные результаты. Не закрывать задачу по наличию кода или документации. Перед новой работой актуализировать status, зависимости и критерии.

## Этап E Нагрузка и масштабирование

- [ ] **E01 · P1 · Load envelope и abuse limits. Статус: small local concurrency fixture PASS; sustained/target envelope pending.** Восемь конкурирующих запросов проверили one-active-run/chat, two-active-runs/user и одинаковые idempotency keys ([QA](validation/2026-10-12-concurrency-fixture/README.md)); это не throughput/OOM доказательство. Измерить очередь, SSE, uploads, introspection, regex, большие histories и несколько пользователей. Добавить необходимые connection/rate/deadline/fairness limits по результатам. **Готово:** зафиксированы поддерживаемая нагрузка и ресурсные ceilings; один пользователь не вытесняет остальных; DB outage и shutdown остаются bounded.
- [ ] **E02 · P1 · Sandbox contention и OOM. Статус: bounded local resource PASS; target/multi-attacker/host envelope pending.** При точных CPU/memory limits compose исправлен PID starvation: четыре workers требуют потолок 128 PIDs, а не 32. Приняты concurrent scripts, CPU timeout, реальный worker OOM при активном здоровом соседе, следующий script и ledger ([QA](validation/2026-10-12-sandbox-resource-qa/README.md)); аварийный exit виден в warn. Shared memory isolation не усилена, production не менялся. Проверить несколько workers в общем cgroup, RPC fan-out, runaway CPU/allocations и supervisor death. **Готово:** нарушитель ограничен; соседние runs не теряют durable state; определены restart и admission policy. Per-worker контейнеры вводить лишь если shared limits не удовлетворяют требованиям.
- [ ] **E03 · P1 · Cached authorization без расширения прав.** По нагрузке E01 определить допустимую cache/negative-cache политику introspection и разделение trust availability. **Готово:** rotation/revocation/stale registry не превращаются в stale permission grant или service-to-human downgrade; ухудшение доступности объяснимо и измерено.
- [ ] **E04 · P2 · Несколько API/worker реплик.** Координация SSE subscribers/disconnect policy, общий artifact storage, migration leadership и recovery при rolling restart. **Готово:** две реплики не создают второй активный run/effect и не ставят pause при живом подписчике другой реплики; отказ одного host не теряет доступные blobs. Выполнять только при потребности в HA/нагрузке.
- [ ] **E05 · P1 · Devtool supply chain. Статус: application graph/full pins/Golden local PASS; devtool graph/update acceptance pending.** L01 подтверждает 171 pin и отсутствие найденных vulnerabilities в текущем Linux application graph. Остались transitive/native лицензии и advisories development tools, реальный Dependabot → lock → review → CI путь и воспроизводимость sqlc. **Готово:** неподходящие лицензии не попадают в поставку; разрешённое GPL исключение ограничено линтером; автоматическое обновление проходит полный gate и не означает автоматического принятия.

## Этап F Дополнительные возможности

- [x] **F01 · Принятое решение · Polling discovery.** Polling — штатная архитектура; Docker events не требуются. Интервал настраивается `discovery.poll_seconds` (пример: 300 секунд), freshness TTL — 3600 секунд. При увеличении интервала увеличить TTL с запасом для нескольких опросов; устаревший snapshot остаётся fail-closed.
- [ ] **F02 · P2 · Remote cancel contract.** Определить безопасный вызов cancel_path, идемпотентный результат и границу уже выполненного эффекта. **Готово:** cancel не выдаёт ложный rollback и не теряет status reconciliation. Поддержка опциональна для каждого сервиса.
- [ ] **F03 · P2 · Opaque service credentials.** Только при реальной потребности: deployment bindings, hash/rotation/revocation секретов, права caller и аудит. **Готово:** секрет не регистрирует новый сервис сам и не расширяет делегацию; не попадает в model/script/logs.
- [ ] **F04 · P2 · WebSocket.** Добавить адаптер поверх тех же command IDs и durable event cursors, если SSE/HTTP недостаточно инициирующим сервисам. **Готово:** вопросы/steering/reconnect/authorization имеют ту же семантику, без второй run state machine.
- [ ] **F05 · P2 · Private inference и большие blobs.** Отдельно спроектировать trusted local provider boundary, обработку приватных данных, object storage/chunk reads и новые native formats. **Готово:** размещение endpoint само по себе не отменяет disclosure policy; доступ и бюджет сохраняются при переносе данных.
- [ ] **F06 · P2 · Субагенты и proactive runs.** Только после отдельного решения продукта. Субагенты — внутренний модуль с ограниченными правами и общим бюджетом; proactive execution требует явного opt-in и триггерного контракта. **Готово:** passive event по-прежнему ничего сам не запускает, child run не расширяет права родителя.

- [x] **F07 · P2 · HTTP partial blob delivery. Статус: implemented / local fixture PASS; production pending.** Artifact и handle content поддерживают byte ranges, HEAD, ETag/If-Range и conditional reads. Нет полной буферизации blob или JS-передачи bytes. Владение, роли и expiry проверяются до conditional responses. [QA](validation/2026-10-12-artifact-range/README.md). Постраничное чтение в scripts также использует прямой seek ([QA](validation/2026-10-12-paged-blob/README.md)). Object storage и новые native model formats остаются F05.
